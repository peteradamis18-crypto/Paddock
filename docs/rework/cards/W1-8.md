## Why it must be irdash and not a script from the lead's session
CLAUDE.md rule 3: the lead's Claude session runs inside a packaged app, and anything it starts that writes under
`%APPDATA%` gets its writes redirected to a private copy that the Stream Deck app never sees (this broke the overlays
install once). irdash runs outside the package (the logon task), already stops and starts Stream Deck (`RestartDeck` /
the watchdog in `irdash.cs`, W0-1) and already sees the add-on connect ("showcase: Stream Deck add-on connected",
`DeckSecret`). So: the lead stages the plugin folder inside the repo, irdash copies it into place and restarts Stream Deck.

## What to build
- `deck-intro\install.ps1 -Stage`: builds `deck-intro\build\com.peter.rigintro.sdPlugin\` exactly as today (manifest with
  `$ver`, page, icons, the bundled profiles) and STOPS there: no package, no Explorer. Without `-Stage` it behaves as
  today (kept for a first-ever install on a new PC, where the package route registers the bundled profiles).
- `dash\src\addon.cs`, static class `AddOn`:
  - `Install()`: reads `Version` from the staged manifest and from the installed one
    (`%APPDATA%\Elgato\StreamDeck\Plugins\com.peter.rigintro.sdPlugin\manifest.json`); same version → "Add-on 1.9.2.0 is
    already installed", nothing restarted. Else: stop Stream Deck the way the watchdog does, replace the folder atomically
    (copy the staged folder to `…sdPlugin.new` beside it, rename the installed one to `…sdPlugin.old`, rename `.new` into
    place, delete `.old`; any failure before the final rename puts the old one back and reports it), start Stream Deck,
    wait up to 30 s for the add-on to connect to irdash (the same signal the showcase logs) and for the deck to be on MAIN
    (`DeckToMain`, W0-1), then answer `{"say":"Add-on 1.9.2.0 installed and running"}`; on a timeout
    `{"say":"Add-on 1.9.2.0 copied, but it has not connected yet - look at the deck"}` with code 409. One log line per
    step ("addon: installing 1.9.2.0 over 1.9.1.0", "addon: Stream Deck back, add-on connected after 6 s").
  - `Status()` → `{"installed":"1.9.1.0","staged":"1.9.2.0","connected":true}` for `GET /api/addon` (read-only list in
    `rigstate.cs`).
  - Hooks for the test: the plugins folder path, the staged folder path, and the stop/start/wait-for-connect steps are
    `Func`/`Action` fields the test replaces; the file moves are real (on a scratch folder).
- Command `addoninstall` through `/api/do` (GuardedDo: it restarts Stream Deck, so never while a session is on; W0-2's
  header rule applies as to every command; `Library.Handles`-style branch in `irdash.cs` answering JSON).
- `tools\addon-update.ps1` (the lead's one-liner): refuses when `irdeck-cli.exe state` is busy (reuse `tests\guard.ps1`'s
  `Get-RigBusy`), runs `deck-intro\install.ps1 -Stage`, calls `http://localhost:8199/api/do?c=addoninstall` with the
  `X-Paddock: 1` header, prints the `say` words, exits non-zero unless they say "installed and running". It never
  touches `%APPDATA%` itself.
- `docs\OPERATIONS.md`: the add-on section now says: bump `$ver`, run `tools\addon-update.ps1`, done; the package route
  only for a brand-new PC.
